================================================================
DETAILED CHANGES
================================================================

1. FLEXIBLE FORM STRUCTURE
--------------------------
BEFORE: 
- Fixed questions in exact positions
- Adding/removing questions required code changes
- Column positions hardcoded (row[6], row[7], etc.)

AFTER:
- Dynamic header reading
- Add/remove questions without code changes
- Columns identified by keywords, not position
- Works with any form structure

FILES CHANGED:
- Created: dynamicProcessor.gs (replaces dataProcessor.gs)
- Updated: config.gs (added SCORE_KEYWORDS, COLUMN_KEYWORDS)

HOW IT WORKS:
- Script reads header row first
- Identifies score columns by keywords (score, rating, quality, etc.)
- Identifies other columns (instructor, course, date) by keywords
- Processes data based on column TYPE, not position

----------------------------------------------------------------

2. SCORING OUT OF 25 (SUM, NOT AVERAGE)
---------------------------------------
BEFORE:
- Each linear scale: 1-5
- AVERAGED to single 1-5 score
- Display: "4.2 / 5"

AFTER:
- Each linear scale: 1-5
- SUMMED for total score
- Display: "21 / 25 (84%)"

FILES CHANGED:
- dynamicProcessor.gs: calculateTotalScore() function
- emailBot.gs: Report HTML templates
- dashboard.js: Score display logic

CALCULATION LOGIC:
- Find all columns with score keywords
- Sum their values (1-5 each)
- Max = count × 5
- Example: 5 questions × 5 max = 25 max score

AUTOMATIC ADJUSTMENT:
- Add 6th rating question → max becomes 30
- Remove a question → max adjusts automatically
- No code changes needed!

----------------------------------------------------------------

3. SINGLE LOGIN ACCESS (DEPARTMENT LEAD ONLY)
---------------------------------------------
BEFORE:
- Multiple user accounts
- QC team had edit access
- Faculty had view access
- Complex permission management

AFTER:
- ONLY Department Lead has login
- No other accounts needed
- Forms are public (anyone can submit)
- Faculty receive email reports (no login)

ACCESS MODEL:
┌─────────────────┬────────────┬───────────────────────┐
│ Role            │ Login?     │ How They Interact     │
├─────────────────┼────────────┼───────────────────────┤
│ Department Lead │ YES        │ Full system access    │
│ QC Team         │ NO         │ Submit forms only     │
│ Faculty         │ NO         │ Receive emails only   │
│ Students        │ NO         │ Submit feedback forms │
└─────────────────┴────────────┴───────────────────────┘

BENEFITS:
- Simpler security
- No password management
- Single point of accountability
- Easier auditing

----------------------------------------------------------------

4. EMAIL BOT WITH GMAIL ACCESS
------------------------------
BEFORE:
- Manual email sending
- Generic reports
- QC Lead sent all emails

AFTER:
- Automated email bot
- Personalized reports to each faculty
- Triggered automatically on form submit
- Weekly summaries sent automatically

FILES CHANGED:
- Created: emailBot.gs (new file)
- Updated: config.gs (EMAIL_SETTINGS)

EMAIL TYPES:
1. Observation Report (immediate) → Specific faculty
2. Weekly Summary (Monday) → All faculty + Lead
3. Low Score Alert (immediate) → Lead only
4. Monthly Report (1st of month) → Lead

EMAIL CONTENT:
- Score displayed as X/25 (not X/5)
- Percentage shown
- Status with emoji (🌟 Excellent, ✅ Good, etc.)
- Score breakdown table
- Feedback details (strengths, improvements)

----------------------------------------------------------------

5. FACULTY EMAIL LIST SECURITY
------------------------------
BEFORE:
- Emails could be anywhere
- No standard storage

AFTER:
- Faculty emails in config.gs (can move to GitHub Secrets)
- JSON format for easy updates
- Name matching (exact and partial)

FORMAT:
{
  "Dr. Smith": "smith@university.edu",
  "Dr. Jones": "jones@university.edu"
}

SECURITY OPTIONS:
1. Store in config.gs (simple)
2. Store in GitHub Secrets (more secure)
3. Store in separate protected sheet (alternative)

================================================================
KNOWN ISSUES & LIMITATIONS
================================================================

1. Gmail Sending Limits
   - Free accounts: 100 emails/day
   - Google Workspace: 2000 emails/day
   - Large departments may hit limits

2. Faculty Name Matching
   - Names in form MUST match FACULTY_EMAILS keys
   - Partial matching supported but exact is better

3. Score Columns
   - Must contain keywords: score, rating, quality, (1-5)
   - If header doesn't match, won't be counted

4. Form Changes
   - After adding questions, existing data unaffected
   - New calculations apply to new submissions only
   - Run reprocessAllData() to recalculate historical
